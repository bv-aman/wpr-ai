# WP Remote API — Working Notes

Single source of truth for the API surface the customer pack builds on.

## Confirmed (2026-11-11, from the official OpenAPI v6 spec)

- **Spec:** https://docs.blogvault.net/api/v6/openapi.json — local reference copy at `docs/openapi-v6.json` (249 paths). This is the contract source of truth.
- **Base URL:** `https://api.blogvault.net/api/v6` (production).
- **Auth:** HTTP Bearer. `Authorization: Bearer <API Token>`. Token format `bvsk…`, generated by the customer in the dashboard at **My Account > API Credentials**. Self-service — no platform blocker for the pack.
- **Async pattern:** mutating POSTs return a task; poll `GET /tasks/{task_id}`; cancel via `POST /tasks/{task_id}/cancel`. Skills must encode poll-until-done.
- **Safety is API-native:** `POST /sites/wp/updates/perform` accepts per-site `options.backup: true` (platform backs up before updating) and `override_lock: false` by default (locked plugins/themes/core are respected). Also per-site `options.sandbox: true` (update via sandbox workflow; exclusive with `backup`) and `options.visual_regression: true` — plan-gated.
- **Pagination (from spec):** page-based — `?page=N&per_page=M`; envelope `{ <items>, meta: { pagination: { page, perPage, totalPages, totalItems } } }`; default perPage 100.
- **`GET /sites` params:** `page`, `per_page`, `timezone`, `sort`, and deepObject `filters` (e.g. `filters[backups:eq]=true`, `filters[tags:in]=428`) — tag filters enable scoped sweeps ("only sites tagged production").
- **Tasks:** poll `GET /tasks/{id}`, envelope `{ task: {...} }`; statuses `initializing | running | completed | cancelled | failed | aborted` (last four are terminal). Task carries `progress`, `details`.
- **`GET /sites` is health-report-grade:** each site object carries `wp.core` (current/latest/update_available/locked), `security.scanner.status`, `uptime.status`, `backups.latest_snapshot`, `server.php_version`, `tags`, `client` — one paginated call powers a full fleet overview.

## Live-verified (2026-11-11, smoke test against the test account)

- Auth works: Bearer `bvsk…` token → `200` on `GET /sites`. Account has 6 test sites.
- **Rate limits:** `X-RateLimit-Limit: 200` per 60 s window (`X-RateLimit-Remaining`, `X-RateLimit-Reset` present). Skills should keep polling cadence modest and batch reads.
- **Pagination param naming quirk:** spec declares `per_page` on `/sites`, but a live call with `?per_page=5` was ignored (returned all 6, `perPage: 100`). Activity-logs endpoint uses `perPage` (camelCase). → **Use `perPage` in skills; verify per-endpoint when first called.**
- `GET /sites/wp/updates` live shape dumped to `tmp/updates-shape.json` (envelope: `{ sites, meta }`).

## Live-verified during flow runs (2026-11-11, see `evidence/`)

- **Update task step chain** (task `details.sites[].steps`): `pre_snapshot` → `update_plugin` (+ `update_plugin_db` for plugins with DB migrations) → `update_theme` → `post_snapshot` → `purge_cache` → `visual_regression` → `wp_test` → `finalize_manage`. Progress via `progress.percent` + metrics. Task input echoes resolved options (incl. `sandbox: false`).
- **Visual regression confirmed working on this account/plan**: returns baseline/comparison/diff screenshot URLs + `percentage_change` per URL. ⇒ backup-first AND post-snapshot are platform-native parts of the update flow.
- **Firewall logs envelope is `{ logs, meta }`** (not `firewall_logs`); entry fields: `id, timestamp, ip_address, country_code, method, path, user_agent, response_code, status, reason, category` (categories seen: `private_ip`, `whitelisted`). Stats endpoint gives 14-day allowed/blocked trends. This test account has **0 blocked events, 0 login attempts** — all logged traffic is allowed.
- **The updates listing only contains items with updates available** (locked items appear with their lock state; fully-updated items drop out entirely).
- **Gap — plan/feature introspection**: no public endpoint reports which options (`sandbox`, `visual_regression`, staging, vulnerability enrichment) the plan supports. Had to verify empirically (VR worked; staging endpoint accessible). Platform ask: feature-flags endpoint.
- **Case observed — "vulnerable with no update path"**: Kadence Blocks PRO Extension v1.6.1 (vulnerable, no VP, no update available via API — license-side update). Skills must report these separately, never force.

## Confirmed from spec (flow research, 2026-11-11)

- **Activity logs (Flow 2 backbone):** `GET /sites/{site_id}/activity-logs` — `page`, `perPage` (max 500, default 25), `sort` (`timestamp,desc`), deepObject `filters`: `timestamp:gte/lte`, `username:eq`, `object_type:eq` (e.g. `plugin`), `event_type:eq` (e.g. `activated`). WP-side events ARE captured (plugin activation etc.), not just WP Remote actions.
- **Correlation sources for Flow 2:** `GET /tasks` filters (`status:eq`, `type:eq` e.g. `wp_site_update`, `created_at` sort); `GET /auto-update-history` filters (`performed_on:gte/lte`, `status:in`); `GET /sites/{id}/security/scanner/cleanup` (cleanup runs); `GET /sites/{id}/snapshots` (backup/restore trail).
- **Firewall logs (Flow 3 backbone):** `GET /sites/{site_id}/security/firewall/logs` — filters include `ip_address:contains` (e.g. `203.0.113`), `status:eq` (`blocked`), `timestamp:gte/lte`; plus `/logs/stats`. Whitelist action exists: `POST .../firewall/ip-access/whitelist`.
- **Staging (sandbox for Flow 1):** `POST /staging-sites` body `{ staging_site: { site_id, snapshot_id, php_version, options } }` — spin a sandbox from a snapshot; SSO into it via `/staging-sites/{id}/wp/users/sso-login-url`.
- **Vulnerability detail (Flow 1 — resolved, live-verified):** `GET /sites/wp/plugins?include_vulnerabilities=true` (same param on `/sites/wp/themes` and `/sites/wp/wordpress-core`) returns per-plugin `security.vulnerabilities[]` with `cvss_rating` (none/low/medium/high/critical), `cvss_score`, `cve_id`, `ghsa_id`, `patched_version`, `published_at`, and `virtual_patch{available, mode, state, live_at, applied, applied_at}` (schema: `SitesWpVulnerabilitySecurity`). **Plan-gated** ("vulnerability enrichment"). Spec quirks: the param is NOT in the parameter list — it is documented only inside the schema description; `with_vulnerabilities` is the name of a response *example*, not a parameter. Live check on the test account: 26 plugins with vulnerability detail, worst CVSS 9.8.
- **Gap — Update Lens:** no mention of "lens"/"UpdateLens" anywhere in the spec. Not API-exposed today. Non-blocking: Flow 1 uses CVSS severity meanwhile.

## Endpoint inventory (grouped; full list in the spec)

- **Sites:** list/create/update/delete, sync start/pause/resume, lock/unlock, subsites, connection key
- **Updates:** list (`GET /sites/wp/updates`), perform (bulk, per-site plugin/theme/core targeting with `target_version`), lock/unlock per asset, WP core lock; auto-update schedules CRUD + enable/disable + history
- **Plugins/Themes:** list, install (from repo), upload, activate/deactivate, delete, lock/unlock
- **Backups:** snapshots list/show, restore, download, upload, migrate, enable/disable, real-time backups enable/disable + events; file/table browsing (list files/tables, versions, stats)
- **Security:** scanner detections (files/scripts/plugins/cron/redirections) + safe/unsafe marking, malware cleanup (eligibility → run → report with diffs), firewall (IP whitelist, geo-blocking, bot protection, logs + stats), login protection attempts/stats, virtual patching (per-site + per-vulnerability), WP user password reset (per-site + fleet-wide), WP security keys rotation, 2FA management
- **WP users:** list/create/delete, role updates, password updates, default login user, **SSO login URL generation**
- **Monitoring:** uptime / SSL / domain / visual / page-content / form monitors — list, show, enable/disable, refresh, probes; PHP monitor logs
- **Staging:** create/show/delete, resume, extend expiry, PHP version update, download, SSO login
- **Performance (Airlift):** enable/disable, settings, reports
- **Reports:** on-demand create + PDF download + send-email; report templates; scheduled reports (pause/resume)
- **Agency/ops:** clients, managed accounts (invite/accept/reject), team members, tags (assign/remove to sites), site notes + activity logs, custom works, important pages, code snippets (validate/execute/versions), sender emails (DKIM etc.), whitelabel branding, backup destinations, email OTP templates

## Capability → candidate POC flows (seed menu)

1. **Fleet update sweep** — list pending updates across all sites → present the plan → perform with `backup: true`, locks respected → poll tasks → report
2. **Weekly health report** — sites + uptime probes + SSL expiry + pending updates + scanner summaries → markdown (optionally scheduled + emailed via API)
3. **Security sweep** — detection summaries + firewall/bot/login stats across the fleet → findings report → optional malware cleanup (eligibility → run → diff review)
4. **Credential operations** — bulk WP password reset / security-keys rotation / 2FA management across sites
5. **One-click login** — "log me into site X" → SSO login URL
6. **New site onboarding** — add site → enable backups/security/monitoring → install standard plugin set → tag → report
7. **Staging workflow** — spin up staging from a snapshot → SSO in → change PHP version → report
8. **Plugin governance** — find/deactivate/delete banned plugins fleet-wide; lock critical versions
9. **Monitoring setup** — enable uptime/SSL/domain monitors + review recent probe results

## Migration & restore (schema-verified 2026-11-19)

- **Migrate** `POST /sites/{id}/backups/{snapshot_id}/migrate` — `{ migration: { destination_url, type: internal|external, scope{include_files, include_database, paths, tables}, connection{method: http|ftp, credentials{server{protocol: ftp|sftp|ftps, host, username, password | private_key, path, port}, database{host, username, password, name}, http_auth}}, options{retain_latest_posts, retain_latest_woocommerce_orders, preserve_permissions, server{ip, name_server}, real_time_events{enabled, until}}} }`. Internal = destination site on the account (HTTP only, must be connected). External = any server via FTP/SFTP/FTPS + direct DB import — **destination does not need the plugin**.
- **Restore** `POST /sites/{id}/backups/{snapshot_id}/restore` — `{ restore: { scope{include_files, include_database, paths, tables, subsite_ids}, connection?, options{...same as migrate}} }`. Omit `connection` entirely = same-site HTTP restore (site must be connected). `method: ftp` = FTP/SFTP/FTPS restore with server creds + **database creds required** — the path for restoring down/disconnected sites. `retain_latest_posts`/`retain_latest_woocommerce_orders` = merge semantics; `real_time_events.until` = point-in-time beyond the snapshot.
- Both return `201 { task }`.
- **Selective-restore catalogs (live-verified 2026-11-19):** `GET /sites/{id}/files` → `{ files: [{ path: "./wp-admin/", type, size, status }] }` (hierarchical, per-item sync status); `GET /sites/{id}/tables` → `{ tables: [{ name: "wp_posts", rows, size, status: synced|skipped }] }` (real table names incl. prefix). These are the authoritative validators for `scope.paths` / `scope.tables` — never guess table names or paths. Update tasks carry their own manifest: `input.sites[].plugins[].filename` = exactly what was updated; `details.sites[].steps` shows `update_plugin_db` (DB-migration caveat for files-only rollbacks) and `pre_snapshot` timing.
- **Scope is inclusion-only** — no exclude lists ("everything except uploads" is not expressible). Platform ask: `exclude_paths`.
- **Gap — no dry-run credential test:** no `test-connection` endpoint for FTP/DB credentials (only backup-destinations have `/test`). Pre-flight is client-side TCP reachability + format checks; the task's first steps fail fast on auth errors before writes. Platform ask: `POST /sites/{id}/backups/test-connection`.

- **Site `health` (show response only):** `{ score: 0-100, uptime_percentage, status: healthy|warning|critical }` — the onboarding headline. Uptime per site: `{ enabled, status: up|down|unknown }`.
- **Gap — GA connection not in public v6** (no google/analytics endpoints): dashboard-only today; the onboarding skill states this honestly instead of faking it. Platform ask: GA connection endpoints (other sites' GA state is also unreadable via API — fleet-convention detection for GA is approximate at best).
